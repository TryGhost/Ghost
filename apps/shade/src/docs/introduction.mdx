# Shade

<p className="excerpt">Shade is the design system that powers Ghost Admin. Tokens, layout primitives, generic UI controls, and product-shaped patterns — all in one place so designers, engineers, and AI agents stop reinventing them.</p>

## In one screen

- **[Tokens](?path=/docs/tokens-tokens-guide--docs)** — colour, type, spacing, radius, motion. Visual galleries in the sidebar.
- **[Primitives](?path=/docs/primitives-primitives-guide--docs)** — `Stack`, `Inline`, `Box`, `Grid`, `Container`, `Text`. Layout, not chrome.
- **Components** — `Button`, `Input`, `Dialog`, `Tabs`… Generic and accessible. Built on Radix + ShadCN.
- **Patterns** — `PageHeader`, `KpiCard`, `Filters`. Product-shaped compositions.
- **Page templates** — `ListPage`, `DetailPage`. Top-level page wrappers that compose patterns.

The boundaries between those layers are the whole point. See **[Layers](https://github.com/TryGhost/Ghost/blob/main/apps/shade/CONTRIBUTING.md#layers)**, in Contributing to Shade, for the decision flow.

## Working in Shade

Shade is the **default source for Ghost Admin UI** and for apps built for Ghost. If a control exists, use it. If it doesn't and you'll reuse it inside Ghost Admin, [Layers](https://github.com/TryGhost/Ghost/blob/main/apps/shade/CONTRIBUTING.md#layers) tells you which folder to add it to.

See **[Contributing to Shade](https://github.com/TryGhost/Ghost/blob/main/apps/shade/CONTRIBUTING.md)** for the implementation and review checklist.

## Imports

Import from the subpath for the layer you need:

| Subpath                          | Contains                                                               |
| -------------------------------- | ---------------------------------------------------------------------- |
| `@tryghost/shade/primitives`     | `Stack`, `Inline`, `Box`, `Grid`, `Container`, `Text`                  |
| `@tryghost/shade/components`     | Generic controls: `Button`, `Input`, `Dialog`, `Table`…                |
| `@tryghost/shade/patterns`       | Product-shaped compositions: `PageHeader`, `KpiCard`, `Filters`…       |
| `@tryghost/shade/page-templates` | Page wrappers: `ListPage`, `DetailPage`                                |
| `@tryghost/shade/utils`          | `cn`, `formatNumber` and other helpers, and the `LucideIcon` namespace |
| `@tryghost/shade/app`            | `ShadeApp` and `useShade`                                              |
| `@tryghost/shade/tokens`         | Token names and the `shadeToken()` helper                              |

```tsx
import {Stack} from '@tryghost/shade/primitives';
import {Button} from '@tryghost/shade/components';
import {PageHeader} from '@tryghost/shade/patterns';
import {ListPage} from '@tryghost/shade/page-templates';
import {cn, formatNumber} from '@tryghost/shade/utils';
```

Page templates have their own subpath: `ListPage` comes from `@tryghost/shade/page-templates`, not `/patterns`. Page templates are top-level page wrappers; patterns are the building blocks they compose.

Never import from the root `@tryghost/shade` barrel or from a deep path into the package, such as `@tryghost/shade/src/components/ui/button`. The subpath makes the layer visible at the call site, which is the first thing a reader needs; the root barrel hides it and encourages cross-layer drift. Inside Shade itself, imports follow [Contributing to Shade](https://github.com/TryGhost/Ghost/blob/main/apps/shade/CONTRIBUTING.md#imports).

## Embedded and standalone setup

Where Shade's stylesheet and `ShadeApp` come from depends on who owns the document:

- **Embedded Admin apps** are bundled into Ghost Admin and render in Admin's own document. Admin owns the single stylesheet and application wrapper, so these apps import neither `@tryghost/shade/styles.css` nor `ShadeApp`; they only import components.
- **Standalone surfaces** own their document. This includes a Ghost app running in an iframe inside Admin, because an iframe doesn't inherit Admin's styles. They import `@tryghost/shade/styles.css` once, in the app stylesheet, and wrap the app in `ShadeApp`.

To set up a standalone surface, follow [Using Shade in a Ghost app](?path=/docs/overview-ghost-apps--docs): install, Tailwind, fonts, `ShadeApp`, theme and page frame.

## Admin 7 milestones

Shade previews use the new controls by default. New screens use ordinary
`Button`, `SelectTrigger`, `InputGroup`, `Badge`, `FilterBar`, and `PageHeader`
components; there is no need to add `shape="pill"` or copy milestone classes into
pages. Form selects and input groups retain standard rounded corners; their
embedded action buttons inherit the button shape. PageHeader.SelectTrigger supplies
the pill shape for header dropdowns. Explicit shapes remain available for a specific visual need.

Admin 7 changes that are still rolling out sit behind Admin's `admin7Design`
Labs flag. Admin passes the flag's value to `ShadeApp`; Shade previews and
standalone surfaces default to `true`, so they show the Admin 7 design:

```tsx
<ShadeApp admin7Design={admin7Design} darkMode={darkMode}>
    <App />
</ShadeApp>
```

Appearance differences belong in Shade's tokens, scoped by the
`data-admin7-design` attribute that `ShadeApp` writes. Components read the same
value only for structural or interaction differences:

```tsx
import {useShade} from '@tryghost/shade/app';

const {admin7Design} = useShade();
```

Portals carry `data-admin7-design` through Shade's internal scope wrapper. Keep
scope attributes off `document.body`: independently mounted surfaces must not
change one another's menus or dialogs. Embedded ActivityPub inherits Admin's
value from the shared application wrapper.

The switch is named after the flag and is removed with it. A later milestone
that needs a Shade switch adds its own, named after its own flag.

The [feature flag guide](https://github.com/TryGhost/Ghost/blob/main/docs/practices/feature-flags.md#admin-7-milestones)
covers naming, shared presentation, testing and removal. Ordinary component
calls already use the intended defaults.
