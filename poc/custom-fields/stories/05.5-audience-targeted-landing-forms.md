# Story 5.5 — Audience-targeted landing forms

**Goal:** let owners create **multiple** Landing forms, each targeting an **audience** (all members / paid only / specific tiers or labels), so they can ask different things of different members.

**Status:** Done. Builds on [Story 5](./05-landing-form.md) (the single-form mechanic).

**Depends on:** Story 5 (injected card, implicit-pending + dismiss, collection flow, preview) — the core mechanic is identical for one form or many. 5.5 only adds *which field set a member gets*.

## Shape (mirrors Newsletters)

The Landing form section becomes a **list of forms**, modelled on the Newsletters UI:

- **Empty state:** no forms yet → show a **placeholder card preview** + an **"Add landing form"** CTA (the Ghost Explore "card when off" pattern). Replaced by the list as soon as one form exists.
- **List state:** Newsletters-style rows — each row is one form: **name** + **description** (subtitle) + an **audience** badge + an **enable toggle** + **Edit** + **drag-to-reorder**. **"Add landing form"** at the top.

## Create vs Edit (mirrors Newsletters)

- **"Add landing form" modal** (like Create newsletter): collects **Name**, optional **Description**, and **Audience**. (Newsletters' "Opt-in existing subscribers" toggle has no analog; the Audience picker takes that slot.) On confirm → adds the row, then opens the Edit modal to pick fields. The button label is **"Add landing form"** in both the empty state and the list header.
- **Edit modal** (the Story 5 `PreviewModalContent`): **General** tab = name + description + the field list (`FormFieldsList`); **Segmentation** tab = the audience picker (now real). Audience set at create stays editable here.

## Audience picker (reuse the Newsletter recipient filter)

Reuse `default-recipients.tsx`'s pattern: a `Select` + a `MultiSelect` fed by `useDefaultRecipientsOptions` (tiers + labels + simple Free/Paid segments). Trim the options to:

- **All members** (`status:free,status:-free`)
- **Paid-members only** (`status:-free`)
- **Specific people** → the tier/label `MultiSelect` (`segment`)

Drop "Whoever has access to the post" (post-scoped, irrelevant) and "Usually nobody". Audience is stored as the same comma-joined NQL-style filter string the picker already emits, so it flows straight into the real query path later.

## Precedence (decided)

- **Order in the list = priority.** A member is assigned to the **first form whose audience matches** them; drag to reorder. **One form per member** (the first match) — completing/dismissing it never cascades to another.
- Not "last created" (non-deterministic) and not "most specific wins" (breaks on overlap without nesting).

## POC matching limit (labels)

Matching in the POC runs **client-side in Portal**, where the member object exposes `status`/`paid`/`subscriptions (tiers)` but **not labels**. So:

- *All members*, *Paid-members only*, *Specific people → tiers* match correctly in the live card.
- *Specific people → labels* is **selectable in admin** (real component, real stored value) but **inert in the live card** — the client can't match it.

This is a POC artifact, not a real constraint. In production, matching is **server-side** (exactly like newsletter recipients): members have a queryable `labels` relation (`members_labels` → `labels`), NQL already supports `label:slug` (`models/member.js`), and Ghost already resolves these filters when sending email. So **labels are no harder than tiers in a real build** — the server picks the matching form for the authenticated member and hands it to Portal. Verified; see [LEARNINGS.md](../LEARNINGS.md).

## Data model change

Story 5's single `forms.landing` (one placement list) + `landingFormEnabled` setting becomes a **`landingForms` list**: each form `{ id, name, description, audience, enabled, fields: placement[] }`. Per-member dismissal becomes **per form**: `dismissed[memberId][formId]`. Cheap to evolve in the localStorage POC; in a real build `audience` is the NQL filter and matching runs server-side. Seed migrates the Story 5 form in (plus a second so precedence is demoable).

## Build order

- **Part A — admin (done):** data model (multi-form list + per-form dismissal); empty-state placeholder card; "Add landing form" modal (name/description/audience); the form list (Newsletters-style `Table`/`TableRow` rows + toggle + Edit + drag-reorder); Edit modal gains name/description + the real Segmentation audience picker.
- **Part B — Portal (done):** match the member to the first form by audience (status/paid/tier; labels inert), show that form's card; per-form dismissal; `?cf_landing` still forces the member's matched form.

## As built (notes)

- **List** reuses the real `Table`/`TableRow`/`TableCell` via `SortableList` `wrapper={Table}` (same as `newsletters-list.tsx`) for matching height/hover/borders + `description || 'No description'`. Header divider via a `border-t` wrapper (the wrapper can't pass `borderTop`). The audience badge was dropped from the row (audience is editable inside the form). Sidebar icon: `user-pen`.
- **Empty state** is a light-only (no dark variants, like the signup iframe preview) faux browser: full-bleed gradient, white site window, full-width URL bar showing `siteData.url`, a minimal post skeleton that masks to transparent at the bottom, and the real card floating bottom-right with the signup-style logo (`portal-splash-default-logo` in an accent circle when no site icon).
- **Card** copy is centered with the subtitle removed; strings go through `t()` (not registered in `ghost/i18n` for the POC — see LEARNINGS).
- **Known gap:** the admin preview is a hand-built mock and drifts slightly from the real Portal card; the fix is to render the real `LandingCard` via a Portal preview iframe (as signup does). See LEARNINGS.

## Done = demoable

Owner creates two forms with different audiences (e.g. All members → Interests; Paid-members only → Company), ordered so Paid wins for paid members → a paid member sees the Company card, a free member sees the Interests card → each fills/saves or dismisses independently. Reordering changes who-sees-what. Empty state shows the placeholder card.

## Out of scope (POC)

Real server-side NQL matching, label matching in the live card, analytics per form, scheduling/timing, more than one form shown per member.
